# ADR-001: Object Detection Model Framework

## Status
Approved

## Context
Real-time, early-stage forest fire detection from drone video streams demands highly localized, low-latency, and robust object detection. Early fire events are marked by small flame pixels or amorphous, diffuse smoke columns that are easily obscured by the forest canopy. The detection model must run either directly on resource-constrained drone edge hardware (e.g., NVIDIA Jetson boards) or be processed rapidly in the cloud with minimal frame queue latency.

---

## Alternatives Considered

1. **Standard Convolutional Image Classifiers (e.g., ResNet-50, EfficientNet-B4)**:
   - *Pros*: Simple training, robust classification.
   - *Cons*: Fails to provide spatial localization (bounding boxes) of the smoke or fire within the video frame.
2. **Vision Transformers (ViTs) for Object Detection (e.g., DETR)**:
   - *Pros*: State-of-the-art spatial relationship learning; handles global context extremely well.
   - *Cons*: Extremely high computational complexity, slow inference rates on edge devices, and requires massive training datasets to converge.
3. **YOLO (You Only Look Once) Framework (v8/v9)**:
   - *Pros*: Single-stage detection enables real-time frame rates ($\ge 30$ FPS); anchor-free head increases accuracy for amorphous objects like smoke; decoupled architecture separates classification and regression tasks.
   - *Cons*: Lower accuracy on very small objects compared to multi-stage detectors (like Faster R-CNN), though mitigated by feature pyramid networks (PANet/FPN).

---

## Decision
Select **YOLOv8/v9** as the primary object detection framework, implemented in PyTorch. 

---

## Justification & Research Alignment
- **Real-Time Inference**: YOLO's single-pass neural network architecture is mathematically optimized for speed, producing inference times under 30ms per frame. This meets the criteria for immediate hazard detection.
- **Edge Deployment**: The availability of compressed sub-variants (YOLOv8-Nano/Small) allows compiling to TensorRT engines, running efficiently on Jetson Orin edge boards without depleting drone battery capacity.
- **Localization Capability**: Bounding boxes provide GPS telemetry coordinate estimates of the fire by translating image pixels to earth coordinates using drone altitude and camera pitch calculations.

---

## Outcome Addendum — 2026-09-10 (Phase 3, real training)

The decision (YOLOv8n) was executed against real data. Two datasets, two label types:

| Run | Data | Base | Config | Result |
| :--- | :--- | :--- | :--- | :--- |
| **Detection** (`wildfire_yolov8n.pt`) | FireNet — 412 train / 90 val, real Pascal-VOC boxes, single class `fire` | `yolov8n.pt` | 50 epochs, imgsz 512, CPU | **mAP@0.5 = 0.733**, mAP@0.5:0.95 = 0.349, P = 0.766, R = 0.739; **CPU FPS = 35.6** |
| **Classification** (`wildfire_yolov8n_cls.pt`) | FLAME frame-level Fire/No_Fire — classification-only, no boxes | `yolov8n-cls.pt` | 10 epochs, imgsz 224, CPU, 4000/class subsample | top-1 acc = _see `results/README.md`_ |

### Result vs targets
- **CV-1 (mAP@0.5 ≥ 88.0%): NOT MET.** Measured 73.3%. This is expected and not softened: FireNet supplies only **412** training images of a **single** class at low resolution, trained **50 epochs on CPU**. The gate's 88% assumed the full FLAME set (47,992 frames) with bounding-box ground truth, which FLAME's classification sub-item does not provide (see below). FireNet is documented as a *secondary* set in `datasets.md`; a production detector needs FLAME-scale box-annotated data (e.g. FLAME's segmentation-mask sub-item converted to boxes) and GPU epochs.
- **CV-2 (FPS ≥ 30): met on CPU** (35.6 FPS for the nano model at 512px on a Ryzen 7 5800H). The gate is *defined* for Jetson Orin + TensorRT, so this is favourable but not a like-for-like confirmation; on-hardware benchmarking remains open.

### Two dated deviations from Phase-1 decisions (recorded here per the "update the ADR" rule)
1. **Bounding-box ground truth.** Phase 1 assumed FLAME would train the detector. The downloaded FLAME frame-level set is **classification-only** (folder = label, no boxes). Rather than treat class labels as fake boxes, Phase 3 trains: (a) a real box **detector on FireNet**, and (b) a whole-frame **classifier on FLAME**, reported separately. The classifier is *not* a detector and is not compared to the CV-1 mAP gate.
2. **70/15/15 "chronological by flight" split.** The FLAME classification sub-item carries **no flight id or timestamp**, so a chronological partition is not possible on this data. Substitute: a **seeded (seed=0) class-stratified random** 70/15/15 split (train+val from `Training/`, test = the separate `Test/` folder untouched). A first attempt using a lexical-order slice produced a degenerate classifier (val acc ≈ chance) due to train/val scene mismatch; the seeded random split corrects it.

The architecture decision itself (single-stage YOLOv8n) stands — it trained cleanly and hit the speed target; the accuracy shortfall is a **data-scale** limitation, not a framework one.
